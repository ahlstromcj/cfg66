Exploring reimplementing ftswalker with <filesystem>
Chris Ahlstrom
2026-03-29 to 2026-03-31

The ftswalker module currently does not compile on Windows... it needs
Gnulib's fts module. Which probably means downloading and building the
whole library on Windows.

So let us look into using the <filesystem> support of C++17.

The functions from ftswalker that we need to support:

    -   File/directory status a la get_fts_type ()
        -   is_directory ()
        -   is_regular_file ()
        -   is_leaving_directory ()
        -   is_other_file_type ()
        -   is_fts_error ()
        -   is_actionable_file ()
    -   Search paths. Can use lib66::tokenization or util::searchpath.
    -   find_file (), which collects full paths where the file is found.
    -   find_regular_files () and collect all the full paths-to-files find.
    -   process_files (function fn, string rgx, comparator cfn)
    -   process_files (bifunction fn, string target, comparator cfn)

Free callback functions:

    -   fts_show_target (const std::string & match, util::ftswalker::FTS ft)
    -   fts_item_copy (string source, string target, util::ftswalker::FTS ft)
    -   fts_copy_directory (const std::string & source, const std::string & dest)
    -   fts_item_delete (const std::string & item, util::ftswalker::FTS ft)
    -   fts_delete_directory (const std::string & path)
    -   compare_files_before_dirs (const ::FTSENT ** first, const ::FTSENT ** second)
    -   fts_find_file (string rootdir, string target)
    -   fts_get_file_path (string rootdir, string target)
    -   fts_find_files_by_regex
    (
        tokenization & collected, const lib66::tokenization & paths,
        string rgx, comparator cfn
    )

The functions from the fts API:

    -   fts_open() and fts_close()
    -   fts_read()
    -   fts_read_entry()

    We observe that when we want to copy a file, the destination is
    *not* the destination *directory*, but the destination *path*.

    You cannot use std::filesystem::copy() to copy to a non-existing
    directory; you have to make sure it exists. Even though as a third,
    optional parameter, it takes std::filesystem::copy_options, there
    is no option to create automatically the needed directory.

    There is also std::filesystem::copy_file() which can only copy
    a single file. The copy() function is void, while the copy_file()
    function returns a bool.

    std::filesystem::path anotherdir2{"yetAnotherTemp"};
    std::filesystem::exists(anotherdir2)                    // false
    std::filesystem::copy(newpath1, anotherdir2);
    std::filesystem::exists("yetAnotherTemp/file1.txt")     // false
    std::filesystem::exists("yetAnotherTemp/file2.txt")     // false
    std::filesystem::exists(anotherdir2)                    // true
    std::filesystem::is_directory(anotherdir2)              // false
    std::filesystem::is_regular_file(anotherdir2)           // true
  
    // copy files

    std::filesystem::remove(anotherdir2)
    std::filesystem::exists(anotherdir2)                    // false

main() is the same as above.

If we need access to the depth and display a directory tree, we can still
do that with recursive_directory_iterator, but we cannot use a range-based
for loop.

void iterate_dir (const std::filesystem::path & root)
{
    for
    (
        auto entry = std::filesystem::recursive_directory_iterator(root);
        entry != std::filesystem::recursive_directory_iterator();
        ++entry
    )
    {
        const auto filename = entry->path().filename().string();
        const auto level = entry.depth();
        if (entry->is_directory())
        {
            std::cout << "directory: " <<filename << '\n';
        }
        else if (entry->is_regular_file())
        {
            std::cout << "file: " << filename << '\n';
        }
        else
        {
            std::cout << "unknown type: " << filename << '\n';
        }
    }
}

The reason is that the value_type of recursive_directory_iterator is
std::filesystem::directory_entry, which has no notion of depth.
By using the range-based version, we lose access to the iterator type.

This section describes more filesystems features.

Recall the ftswalker module:

    -   File/directory status a la get_fts_type ()
        -   is_directory ()
        -   is_regular_file ()
        -   is_leaving_directory ()
        -   is_other_file_type ()
        -   is_fts_error ()
        -   is_actionable_file ()

    -   <filesystem>
        -   is_block_file()
        -   is_character_file()
        -   is_directory()
        -   is_empty () checks whether the given path refers to an empty
            file or directory
        -   is_fifo () checks for a named pipe
        -   is_other()
        -   is_regular_file()
        -   is_socket()
        -   is_symlink()
        -   status_known()

    These functions have three overloads (examples):

        bool is_character_file(std::filesystem::file_status s)
        bool is_character_file(const std::filesystem::path & p)
        bool is_character_file
        (
            const std::filesystem::path & p, std::error_code & ec
        )

    class file_status has information about the type
    [std::filesystem::file_type, an enum class with members none,
    not_found, regular, symlink, etc.] and permissions
    [std::filesystems::perms, a bit set with values on none, owner_read
    (S_IRUSR), etc.
